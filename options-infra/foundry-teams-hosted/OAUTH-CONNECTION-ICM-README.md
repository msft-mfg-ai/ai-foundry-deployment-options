# ICM handoff: custom OAuth MCP connection is converted to invalid DirectInvoke connector

## Suggested ICM title

**Foundry project connection creation converts custom MCP OAuth2 connection to
Connector Gateway DirectInvoke and requires an unrelated OpenAPI v3 definition**

## Summary

Creating a Microsoft Foundry project connection for a custom MCP server with
OAuth identity passthrough fails before the Toolbox is deployed.

The requested connection is:

- category: `RemoteTool`;
- protocol group: `GenericProtocol`;
- authentication: `OAuth2`;
- custom OAuth public client with no client secret;
- MCP endpoint as the connection target;
- `useCustomConnector: false`;
- `useWorkspaceManagedIdentity: false`.

The `Microsoft.CognitiveServices` ARM resource provider ignores or overrides
the requested non-custom-connector behavior. It tries to create a Connector
Gateway custom connector in `DirectInvoke` mode and rejects the operation
because no OpenAPI v3 definition was supplied:

```text
ConnectorNamespaceCustomConnectorDirectInvokeRequiresApiDefinitionV3
```

An OpenAPI definition is not appropriate here: the target is an MCP endpoint,
and an existing connection with the same intended OAuth2/MCP shape works
without one.

## Customer impact

- The Cloud Helper MCP server cannot be added to the OTIS Foundry project with
  OAuth identity passthrough.
- Foundry therefore cannot issue per-user consent links, store user OAuth
  credentials, or refresh them with `offline_access`.
- The dependent `teams-user-tools` Toolbox cannot be deployed against the
  intended OAuth connection.
- The hosted Teams agent cannot call Cloud Helper as the multiplexed Teams
  user.
- `UserEntraToken` is not a viable substitute. It requires a delegated user
  token on Toolbox egress and fails for this hosted-agent path.

This blocks the end-to-end scenario but does not affect the public Toolbox,
PowerPoint skill, Code Interpreter, or ordinary model responses.

## Required provisioning order

The intended deployment order is:

1. Create the Foundry `cloud-helper` OAuth2 project connection.
2. Read the `redirectUrl` generated by Foundry.
3. Register that URL as a Web redirect URI on the Cloud Helper Entra
   application.
4. Create or publish the `teams-user-tools` Toolbox referencing the local
   `cloud-helper` project connection.
5. Deploy the hosted agent referencing that Toolbox.

The observed failure is at step 1. It is not caused by creating the Toolbox
before the connection.

## Expected behavior

The following ARM payload should create an OAuth identity-passthrough
`RemoteTool` connection for an MCP server:

```json
{
  "properties": {
    "category": "RemoteTool",
    "group": "GenericProtocol",
    "target": "https://cloud-helper-mcp-nhicuyifswrqa.azurewebsites.net/mcp",
    "authType": "OAuth2",
    "isSharedToAll": false,
    "useCustomConnector": false,
    "useWorkspaceManagedIdentity": false,
    "metadata": {
      "type": "custom_MCP"
    },
    "credentials": {
      "clientId": "7013b646-eec3-45e5-a488-2f7133c78c5e",
      "clientSecret": ""
    },
    "authorizationUrl": "https://login.microsoftonline.com/e3320f01-1a95-463a-8814-fc63d1c07cef/oauth2/v2.0/authorize",
    "tokenUrl": "https://login.microsoftonline.com/e3320f01-1a95-463a-8814-fc63d1c07cef/oauth2/v2.0/token",
    "refreshUrl": "https://login.microsoftonline.com/e3320f01-1a95-463a-8814-fc63d1c07cef/oauth2/v2.0/token",
    "scopes": [
      "https://cloud-helper-mcp-nhicuyifswrqa.azurewebsites.net/mcp/mcp.access offline_access"
    ]
  }
}
```

Expected response properties:

```json
{
  "authType": "OAuth2",
  "category": "RemoteTool",
  "group": "GenericProtocol",
  "useCustomConnector": false,
  "useWorkspaceManagedIdentity": false,
  "redirectUrl": "https://global.consent.azure-apim.net/redirect/<generated-connector-name>"
```

Foundry should subsequently return an `oauth_consent_request` for a user who
has not authorized the connection. After consent, Foundry should securely
store and refresh the user's credential.

Official behavior is documented at:

<https://learn.microsoft.com/azure/foundry/agents/how-to/mcp-authentication#oauth-identity-passthrough>

## Reproduction

The commands below contain identifiers and public OAuth configuration but no
secret values.

```bash
PROJECT_ID='/subscriptions/5388b7ee-d59c-4634-b5e6-8dcab813db19/resourceGroups/rg-hosted-teams-agent-e332-v2/providers/Microsoft.CognitiveServices/accounts/ai-foundry-vdk23tvr62epc/projects/ai-project-vdk23tvr62epc-1'
TENANT_ID='e3320f01-1a95-463a-8814-fc63d1c07cef'
CLIENT_ID='7013b646-eec3-45e5-a488-2f7133c78c5e'
TARGET='https://cloud-helper-mcp-nhicuyifswrqa.azurewebsites.net/mcp'
SCOPE='https://cloud-helper-mcp-nhicuyifswrqa.azurewebsites.net/mcp/mcp.access offline_access'
OAUTH_BASE="https://login.microsoftonline.com/${TENANT_ID}/oauth2/v2.0"

BODY=$(
  jq -n \
    --arg target "$TARGET" \
    --arg clientId "$CLIENT_ID" \
    --arg authorizationUrl "$OAUTH_BASE/authorize" \
    --arg tokenUrl "$OAUTH_BASE/token" \
    --arg scope "$SCOPE" \
    '{
      properties: {
        category: "RemoteTool",
        group: "GenericProtocol",
        target: $target,
        authType: "OAuth2",
        isSharedToAll: false,
        useCustomConnector: false,
        useWorkspaceManagedIdentity: false,
        metadata: {type: "custom_MCP"},
        credentials: {
          clientId: $clientId,
          clientSecret: ""
        },
        authorizationUrl: $authorizationUrl,
        tokenUrl: $tokenUrl,
        refreshUrl: $tokenUrl,
        scopes: [$scope]
      }
    }'
)

az rest \
  --method put \
  --url "https://management.azure.com${PROJECT_ID}/connections/cloud-helper?api-version=2025-04-01-preview" \
  --body "$BODY" \
  --output json
```

Result: HTTP `400` with
`ConnectorNamespaceCustomConnectorDirectInvokeRequiresApiDefinitionV3`.

## azd CLI limitation

The latest installed `azure.ai.connections` extension also cannot create the
required public-client connection. Passing an empty client secret:

```bash
azd ai connection create cloud-helper \
  --project-endpoint '<project-endpoint>' \
  --kind remote-tool \
  --target 'https://cloud-helper-mcp-nhicuyifswrqa.azurewebsites.net/mcp' \
  --auth-type oauth2 \
  --client-id '7013b646-eec3-45e5-a488-2f7133c78c5e' \
  --client-secret '' \
  --authorization-url 'https://login.microsoftonline.com/e3320f01-1a95-463a-8814-fc63d1c07cef/oauth2/v2.0/authorize' \
  --token-url 'https://login.microsoftonline.com/e3320f01-1a95-463a-8814-fc63d1c07cef/oauth2/v2.0/token' \
  --refresh-url 'https://login.microsoftonline.com/e3320f01-1a95-463a-8814-fc63d1c07cef/oauth2/v2.0/token' \
  --scopes 'https://cloud-helper-mcp-nhicuyifswrqa.azurewebsites.net/mcp/mcp.access offline_access' \
  --force \
  --no-prompt
```

fails locally with:

```text
BYO OAuth2 requires: --authorization-url, --token-url, --client-id,
--client-secret. Missing: --client-secret
```

Current Foundry documentation says the client secret is optional depending on
the OAuth application. The extension's validation therefore prevents using
the documented public-client scenario.

Adding a fabricated secret is not an acceptable workaround. It changes the
OAuth client model and can expose or persist invalid credential material.
