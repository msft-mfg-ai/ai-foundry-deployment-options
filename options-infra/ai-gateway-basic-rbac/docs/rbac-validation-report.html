1. What was tested

This harness proves the customer's Foundry access-control matrix on a live deployment. It:

  1. Deploys a Foundry account + project + APIM inference gateway in a VNET-ready pattern (Bicep).
  2. Creates 6 service principals, one per persona, each with exactly one Foundry role at the right scope.
  3. Runs 37 test cases across 6 suites — every case writes an evidence row (JSON + CSV) with expected vs. actual HTTP status.
  4. Layers an Azure Policy (deny-cognitive-services-model-deployments, empty allow-list) at subscription scope for defense-in-depth against model deployment even if RBAC were mis-configured.

Defense-in-depth for model deployment: On top of RBAC (N-03 shows a builder is denied at 403 via role permissions), the deployment installs a subscription-scope Azure Policy deny-cognitive-services-model-deployments with an empty allowedModels array. This blocks Microsoft.CognitiveServices/accounts/deployments PUTs from ANY identity — even Foundry Account Owner or subscription Owner — so only models pre-baked into the APIM gateway can be reached.
Defense-in-depth for AI Search index authoring (N-09 / N-10):
  1. No Foundry role grants Search dataplane actions — a Foundry User calling PUT /indexes/{name} with a valid Entra ID token is denied at the Search dataplane (N-09).
  2. disableLocalAuth: true on the Search resource — admin/query keys cannot be issued or used, so even a leaked key or a compromised listAdminKeys call would be useless (N-10).
  3. Only the project's managed identity gets access, and only as Search Index Data Reader — query-only, no index authoring. Index creation happens in CI/Bicep, not from user-facing surfaces.
Together these mean users can build knowledge-grounded agents (the project MI queries at runtime) but cannot create, modify, or discover indexes on the underlying Search service.

4. Known gaps — where the customer requirements are NOT met

❌ Gap 1 — Foundry User cannot create guardrails.
Customer requirement: “Users must be able to configure guardrails.”
Observed: Signed into the Foundry portal as Joe (Foundry User at project scope), the Guardrails / Content Safety configuration surface is hidden or read-only. Creating a new guardrail requires Foundry Project Manager or higher.
Impact: Builders cannot self-serve guardrail configuration — a project admin has to do it for them, breaking the “builders own the full agent lifecycle” expectation.
Options:
  1. Elevate the builder persona to Foundry Project Manager at project scope. Trade-off: the builder can then also assign the Foundry User role to other users (conditional roleAssignments/write), which may or may not be acceptable to the customer.
  2. Keep Foundry User and treat guardrail configuration as an admin-only activity documented in the ops runbook (project admin runs it on request).
  3. Escalate to Microsoft to expose guardrail configuration to Foundry User — this is a role-definition gap, not a Bicep/policy issue.
❌ Gap 2 — Foundry User cannot attach tools to an agent from the portal.
Customer requirement: “Users must be able to create tools / skills.”
Observed: Signed into the Foundry portal as Joe (Foundry User at project scope), the agent editor’s “+ Add tool” affordance is either hidden or disabled. However, the API path works — test B-03 in this harness programmatically creates an agent with an MCP tool attached using Joe’s credentials and it succeeds.
Impact: Builders can ship tool-enabled agents through IaC/CI (Bicep + agents_v2/create_agents.py) but cannot self-serve them from the portal — contradicts the “builders own the full agent lifecycle” expectation.
Options:
  1. Elevate the builder persona to Foundry Project Manager at project scope. Same trade-off as Gap 1 (they also gain conditional roleAssignments/write).
  2. Automate tool attachment via CI — keep Foundry User and have builders wire tools through the agents_v2/create_agents.py pipeline instead of the portal.
  3. Escalate to Microsoft — the UI is more restrictive than the underlying role; the “+ Add tool” control should be visible whenever agents/write is granted, which Foundry User has.
❌ Gap 3 — Foundry Project Runtime User cannot invoke the Responses API.
Observed (R-03a): A principal with only Foundry Project Runtime User gets HTTP 403 “does not have permissions for AIServices/agents/write” when calling POST /openai/v1/responses against a v2 agent. The endpoint enforces agents/write but the role only grants responses/*.
Practical workaround: use Foundry User for runtime apps until Microsoft closes the check (R-03b confirms this works).

Purpose. Least-privilege role for principals that need to call an already-deployed agent's interact endpoint and nothing else. Does NOT grant Responses API, agent management, project reads, or keys.
